## Core premise

**Never fill a login form except on the tinyauth / IdP origins** —
everything else (group gate, session) stays tinyauth's job; the broker only
types. Origins whitelist: `auth.pmo.city`, `auth.aikumi.app`.

## Phase A — core path (reuses the W1 green chain: Vaultwarden → base64 0600+shred → CDP)

1. **Watcher service** — new supervisord program `sso-broker.py` in the
   viewer: polls kiosk Chrome via CDP every ~1–2 s; detects a tab whose URL
   matches `auth.pmo.city` or `auth.aikumi.app` (the tinyauth redirect).
   Turns the W1 one-shot into a daemon.
2. **Credential fetch** — Vaultwarden share-vault item per employee (test
   item `cloudbrowser-w1-test` already exists); map `remote-email` → item via
   the broker plumbing; never into LLM context/audit.
3. **Trusted fill + submit** — username/password via CDP injection (W1
   pattern), click Log in, wait for the tinyauth callback → session cookie.
   Timeout + retry.

## Phase B — 2FA & reliability

4. **TOTP leg (D2 hook)** — Authentik asks for TOTP → broker computes it from
   the same vault item and fills it; if no secret → stop + notify → agent
   prompts you in chat (the hybrid 2FA leg). — **IMPLEMENTED 2026-08-26
   (spec 73)**: the slot broker handles the Authentik code stage
   (`ak-stage-authenticator-validate-code`, `input[name=code]`):
   seed from the owner's vault item (grant path) → autonomous fill; no
   seed → router `/otp/*` code-exchange → the agent asks the employee in
   chat and submits the code. Logs are status-only; codes never logged.
5. **Session health** — verify the named TinyAuth cookie (not any arbitrary
   `.pmo.city` cookie), confirm the app tab loads without bouncing back to
   login, and proactively re-login before the 24 h expiry. — **IMPLEMENTED,
   COMMITTED AND LOCALLY VERIFIED 2026-08-26 (`5d3098f`, security hardening
   follow-up pending commit); DEPLOYMENT/LIVE VERIFICATION PENDING ON COOLIFY
   API AUTH RECOVERY**: periodic controller requires the exact deterministic
   TinyAuth cookie `tinyauth-session-39fcd0f6` at `.pmo.city` `/` with Secure
   and HttpOnly, rejects duplicates and CDP errors, validates a freshly issued
   cookie against TinyAuth's authenticated user context and the canonical slot
   owner, deletes only that cookie inside the proactive window, and reloads one
   existing explicitly allowlisted PMO City app tab. It never creates/evicts
   tabs or navigates Authentik/Vaultwarden/error pages. Adversarial unit
   regression: PASS.

## Phase C — hardening & pilot

6. **Restart resilience** — profile archive deliberately strips identity
   cookies (spec 56), so correctness requires a fresh owner-bound login after
   every wake/recreate rather than cookie carry-over. The broker is an
   autorestarting supervisord process, reconnects to CDP, re-resolves the
   current owner's GrantHub item and handles the restored app tab's redirect.
**IMPLEMENTED AND COMMITTED (`5d3098f`); deployed to `cb-fleet-v2`; live
   `/restart` recovery was previously exercised, while full-recreate
   qualification was inconclusive because the owner session expired before the
   destructive boundary.**
7. **Security** — origin whitelist (only the two auth hosts), event-level
   logging only, no plaintext anywhere, kill-switch env
   `SSO_BROKER_ENABLED=false`.
8. **Pilot verification (you + testers)** — clear kiosk cookies → open Files
   → auto-login → list shows; restart ×2; assert a non-PMOC tester still gets
   denied (broker must not bypass the gate).
9. **Docs + mirror** — this spec, W2 table row → done checklist, scrubbed
   template mirror.

## Credential provisioning v3 — session-reuse (2026-08-19, deployed ✅)

The host-side refresh script no longer logs in with the master password.
Final design (evolved through live probing):

- `sso-creds-provision.sh` v3: reads the gateway's live `BW_SESSION` from
  `/proc/<gwpid>/environ`, runs `bw get item --session` with
  `XDG_CONFIG_HOME=/opt/data/bw-cli-state` (isolated from `.hermes`), base64s
  the creds, SSHes to mother01, writes 0600 into the viewer scripts volume.
  Zero login, zero master-password usage, zero state under `.hermes`.
- **Why not the REST API key** (`client_credentials`)? Probed live:
  - password grant: Vaultwarden 1.32+ rejects plaintext master passwords and
    the 2026 bw SDK's client-side KDF hash is not the classic
    PBKDF2 → b64(sha256(mk)) (3 variants probed, all rejected while `bw login`
    with the same creds succeeds).
  - client_credentials: authenticates (needs SDK device fields on ALL grants),
    but the API key **cannot decrypt** — every cipher field comes back
    encrypted (`2.<b64>|<b64>|<b64>`). Only a user-key session can read item
    values, so session reuse is the only clean automation path.
  - `BW_API_KEY_ID`/`BW_API_KEY_SECRET` env vars are now UNUSED — may be
    removed from the hermes Coolify env.
- **bw state isolation**: `XDG_CONFIG_HOME=/opt/data/bw-cli-state` exported in
  `bw-session.sh` + the boot slot script (verified live across 3 clean boots:
  08:21, 13:52, 14:01; old dirs untouched). Never `rm -rf` bw state.
- **/opt/data wipe lesson (2026-08-19)**: a Coolify redeploy wiped `/opt/data`
  (fresh passwd home). Restored from the repo; the repo copy is now the
  canonical source for this script. SSH known_hosts lives at
  `/opt/data/.ssh/known_hosts` (ssh reads the PASSWD home, not `$HOME`) →
  script uses `StrictHostKeyChecking=accept-new` to self-heal after wipes.
- E2E verified: script exit 0 silent; viewer file 0600 root, decodes to
  username_len=10 / password_len=16 (matches the vault item).
- Next: optional cron (e.g. daily) — manual for now.

## Phase C design lock — 2-account model + consent/YOLO (2026-08-19, Tigo ✅)

Production target for the human "log me into my sites" use case. Locked in
discussion; supersedes the 3-account pilot scaffolding.

### Account model (production = 2 accounts, not 3)

1. **Human's Vaultwarden user account** — the employee's own site credentials
   (CRM, portals…). One-time unlock (session, not stored password) → agent
   reuses the session; master password never re-entered, never stored.
2. **Agent's own Vaultwarden account** — the agent runtime's secrets (tokens,
   service creds), auditable separately from the human's items. Kept separate
   for isolation + audit (matches "own bot/vault per instance" rule).

**Retired:** the pilot-era **cloudbrowser service account** (system creds for
unattended shared-kiosk SSO, borrowed via gateway session-reuse). It dies when
browsers go per-employee: the browser's identity *is* the human (Authentik
login as themselves), so no system account exists to feed. Migration path =
retire the scaffold with D1 (per-user browsers).

### Credential-delivery policy (per-use consent, default; YOLO opt-in)

- **Default mode:** before injecting a credential, the agent asks the human:
  *"use credential X for site Y?"* — explicit per-use consent.
- **YOLO mode:** the human may pre-authorize full access (whole vault or a
  named collection, their choice); the agent then fetches + injects without
  asking. YOLO is a human decision per agent/scope, reversible at any time.
- **Both modes:** plaintext never enters the LLM context/audit — the
  deterministic broker (CDP injection) types directly. Same rule as W1.
- The broker's login-fill (tinyauth/IdP origins) is the only exception that
  needs no consent — it is the browser's own identity gate, not a site login.
